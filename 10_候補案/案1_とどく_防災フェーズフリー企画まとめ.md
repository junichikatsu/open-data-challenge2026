## 1. 一言で

公共交通が止まったとき、「今いる場所から、今の自分の身体条件で、どこへ安全に届けるか」を地図で示すアプリ。
平時はバリアフリー経路検索として毎日使われ、運休や警報を検知すると同じ画面が「届く範囲」の地図に切り替わるフェーズフリー設計。狙いは最優秀賞。

## 3. 2026年に顕在化した社会課題

2026年は7月の熊本地震（震度7）と8〜9月の都市型豪雨が相次ぎ、「公共交通が止まった瞬間に、人が目的地にも避難先にも届かなくなる」という課題が全国で同時に露呈した。

| 日付 | 出来事 | 公共交通への影響 | 浮かび上がった課題 |
| --- | --- | --- | --- |
| 5/29 | 新たな防災気象情報の運用開始 | 警報に警戒レベルが付記、気象防災速報を新設 | レベル3で動く人を交通情報と結び付けて誘導する仕組みがない |
| 6/27〜28 | 台風7号・8号が首都圏に接近 | 房総・伊豆特急が終日運休、東京メトロが出入口閉鎖を予告 | 事業者ごとに分散した計画運休情報を利用者が自分で引き直す負担 |
| 7/28 | 令和8年熊本地震（M7.1、最大震度7） | JR九州全線停止、新幹線で約180人が車中泊。九州新幹線 熊本〜新水俣は9/18、鹿児島本線 宇土〜八代は10/10、肥薩おれんじ鉄道は10/13再開。産交バス八代営業所12路線が全便運休 | 避難所465か所に9,872人。徒歩15分で避難所に着ける避難需要は6割、車が使えれば99%。道路の3%遮断で22,381人が救急医療30分圏外、その39.3%が65歳以上（RIETI） |
| 7〜8月 | 外国人被災者の孤立（熊本） | 防災無線が日本語のみで避難所の存在すら伝わらず、3日間寮に留まった事例 | 多言語・やさしい日本語で「どこへ、どう行けるか」を届ける手段の欠如 |
| 8/13〜14 | 令和8年8月千葉豪雨（22市町にレベル5特別警報） | 帰宅時間帯にJR・京成が運転見合わせ。成田空港に6,000人以上が滞留、JR蘇我駅の約4,000人を自衛隊がバス輸送、県庁に1,000人以上 | 「止まる」が分かっても「どこで待ち、いつ動けるか」が分からない |
| 9/8 | 名古屋豪雨（千種区で1時間104.5mm、東海豪雨超え） | 市営地下鉄が17:15に全線停止、市バス終日運休、JR・名鉄・近鉄も停止。帰宅困難者が一時滞在施設で一夜 | 東海3県で265万人に避難指示。地下駅からの脱出と冠水を避けた徒歩経路の案内がない |
| 9/19〜22 | 台風25号（伊豆諸島で総降水量800mm） | 400便以上欠航、関東で運転見合わせ、千葉で土砂崩れにより鉄道が長期不通 | 復旧期の迂回・代行バス情報が日々変わり、既存の経路検索が追従しない |

### 横断する3つの構造

1. **情報は存在するが、経路に引き直されていない。** 運休・警報・道路規制・一時滞在施設は別々に公開されており、「今いる場所から、今の自分に、どこへ届くか」を答えるものがない。
2. **困るのは移動制約のある人から順番。** 高齢者、地下駅・空港の滞留者、車椅子・ベビーカー・外国人が平時の情報設計から取り残されている。
3. **発災直後より復旧期が長い。** 熊本の鉄道復旧は2.5か月。代行バスやデマンド交通が暫定ダイヤで動く期間こそ、経路検索への反映が求められる。

2026年1月改定と報じられた内閣府「帰宅困難者等対策のガイドライン」は帰宅困難者への情報提供のあり方を論点にしており、本案はこの政策文脈に直接応答する（改定時期は一次資料で要確認）。

## 4. 解決したい課題とペルソナ

解く課題: 「公共交通が止まったとき、いまいる場所から、いまの自分の身体条件で、どこへ安全に届けるかが分からない」。
復旧を早めるのではなく、今ある資源（動いている路線、一時滞在施設、避難所、代行バス）に人を「届ける」ことに絞る。

| ペルソナ | 場面 | 困りごと |
| --- | --- | --- |
| A. 都心の通勤・通学者（主対象） | 帰宅時間帯に鉄道とバスが同時停止（名古屋・千葉型） | 帰れるのか、待つのか、どこで待つのか |
| B. 車椅子・ベビーカー・高齢の利用者（主対象） | 地下駅で運転見合わせ、出入口閉鎖、エレベーター停止が重なる | 段差なしで地上に出られる出口と、坂を避けて行ける滞在先 |
| C. 被災地の住民・外国人住民 | 復旧期に代行バスとデマンド交通が暫定ダイヤで動く | 暫定ダイヤがPDFと張り紙にしか存在しない。日本語の防災無線が分からない |
| D. 自治体防災担当・交通事業者 | 発災前の計画、発災中の施設開設判断、復旧期の代替交通設計 | どの路線が止まると誰がどこに届かなくなるか、到達可能性ベースの根拠がない |

主対象は A と B。審査員が身体で理解できる都心の場面で、必須データが最も濃い。C は GTFS-Flex と多言語化で、D は同じエンジンを流用した分析画面で対応する。

## 5. コンセプトと提供価値

**「最短経路」ではなく「到達可能性」を主役にする。**
現在地から動いている手段と自分の足で安全に行ける範囲を到達圏として描き、その中の滞在先・避難所・動いている駅を「届く場所」として示す。到達圏は運休・気象警報・浸水想定・エレベーター稼働状況・身体条件で動的に縮小・拡大する。

| フェーズ | 利用者が見るもの | エンジンがやっていること |
| --- | --- | --- |
| 平時「いつもの経路」 | 段差・勾配を避けたドアツードア経路、駅構内のエレベーター経由 | GTFS + GTFS-Pathways + ほこナビを一つのグラフとして探索 |
| 発災時「とどくマップ」 | 届く範囲と、その中の滞在先・避難所・動いている駅。「帰れる / 待つ / 避難する」の推奨と理由 | 運休・警報・浸水想定・設備停止で辺を切り、同じ探索を到達圏計算に転用 |
| 復旧期「かわりの足」 | 代行バス・デマンド交通を含む暫定ダイヤでの経路。やさしい日本語と多言語 | GTFS-Flex と暫定 GTFS を差し替えて同じグラフを再構築 |

提供価値:
- 利用者に: 「止まった」で終わる通知を「だからこうする」に変える。身体条件と言語を問わず同じ品質で届く場所を示す。
- 自治体・事業者に: 「この路線が止まると誰がどこに届かなくなるか」を事前に計算できる（EBPM）。
- データ提供者に: Pathways のエレベーター情報、RT の運休情報、Flex のゾーン定義が「命に関わる場面で効く」ことを実証する。

位置づけ: PIEN（2022）「止まったことを知らせる」→ Safe Pedal（2025）「安全な経路を選ぶ」→ とどく「止まったときに届く場所を選ぶ」。

## 6. 主要機能と利用シナリオ

| # | 機能 | 利用者に見えるもの | 使うデータ | 優先 |
| --- | --- | --- | --- | --- |
| 1 | とどくマップ（到達圏） | 15・30・60分で届く範囲。運休や警報で範囲が縮み、理由が一行で出る | GTFS、GTFS-RT、ODPT運行情報、気象庁警報、PLATEAU浸水想定 | 必須 |
| 2 | 届く場所リスト | 到達圏内の一時滞在施設・避難所・動いている駅を「届く順」に並べ、推奨を一つ示す | 東京都オープンデータ（一時滞在施設・避難所）、指定緊急避難場所 | 必須 |
| 3 | 段差なし脱出ルート | 地下駅から動いているエレベーターだけで地上に出る経路。停止設備は赤で消える | GTFS-Pathways（都営大江戸線等）、ほこナビ、エレベーター稼働情報 | 必須 |
| 4 | かわりの足（復旧期） | 不通区間を代行バスやデマンド交通で繋いだ経路。予約期限と連絡先が出る | GTFS-Flex、暫定GTFS | 後半 |
| 5 | やさしい日本語・多言語 | 「避難所」を「にげるところ」と表示。英・中・越・ネパール語 | UI辞書、ODPT駅名多言語属性 | 後半 |

利用シナリオ（名古屋 2026-09-08 を再現）:
1. 朝・平時: ペルソナBが車椅子プロファイルで通勤検索。駅構内のエレベーター経由と屋外の緩勾配経路が一続きで出る。
2. 17:15・発災: 地下鉄全線停止。地図が「とどくマップ」に切り替わり、徒歩で届く範囲と一時滞在施設が出る。冠水想定エリアを通る経路は除外。
3. 17:20・判断: 「帰宅は推奨しない。徒歩8分の〇〇ホールで待つ」と理由付きで表示。段差なしで地上へ出る出口も示す。
4. 翌朝・復旧期: 一部路線が再開し到達圏が広がる。不通区間は代行バスで繋がった帰宅経路が出る。
5. 自治体モード: 「大江戸線と都営バスが止まる」を入力すると、徒歩30分圏に一時滞在施設がないエリアと昼間人口が出る。

審査では時刻スライダーで17時台を再生し、運休が入るたびに到達圏が縮む様子を見せる（WOW体験と1分デモを同時に満たす）。

## 7. 技術構成と活用データ

構成の要: 路線・駅構内・歩行空間を一つのグラフに統合し、運休や警報に当たる辺を落とすだけで平時と発災時を同じエンジンで扱う。

```
[公共交通 GTFS/RT/運行情報] [駅構内 Pathways/ほこナビ] [復旧期 Flex/暫定GTFS] [災害情報 気象庁/PLATEAU] [滞在先 東京都]
                    ↓
  統合マルチモーダルグラフ（動的切断: 運休 / 警報 / 浸水想定 / エレベーター停止 / 身体条件）
                    ↓
  到達圏エンジン（Rust → WASM、ブラウザ内、1秒未満）  ←  シナリオ再生（記録した GTFS-RT を時刻で再生）
                    ↓
  [いつもの経路] [とどくマップ] [かわりの足] [自治体モード]
```

| 層 | 採用技術 | 理由 |
| --- | --- | --- |
| 地図描画 | MapLibre GL JS + MVT、地理院標高タイルを Terrain-RGB 化 | PLATEAU を CesiumJS で広域描画するより軽く、スマホで滑らか（資料2の結論） |
| 経路・到達圏計算 | Rust → WASM、Web Worker で実行 | 多層グラフ探索を UI スレッドから切り離す |
| データ取り込み | GTFS / RT / Pathways / Flex を事前にグラフへ変換し静的配信、RT と警報のみ定期取得 | サーバーを薄くし無償公開を維持しやすい |
| 浸水・災害リスク | PLATEAU 浸水想定（CityGML → GeoJSON）、国土数値情報 | 歩行辺に水深属性、警報発表時のみ切断条件として有効化 |
| 滞在先 | 東京都オープンデータの一時滞在施設・避難所、地理院の指定緊急避難場所 | 到達圏との重ね合わせで「届く場所」を列挙 |

## 8. 審査基準との対応と差別化

| 審査基準 | 本案の答え | 証拠として見せるもの |
| --- | --- | --- |
| 社会課題解決 | 2026年に実際に起きた帰宅困難・避難到達の問題を固有名詞と数字で語れる | 名古屋・千葉・熊本の実例、RIETI の到達率分析、帰宅困難者ガイドラインへの直接回答 |
| オープンデータ活用のインパクト | 公共交通 × 気象庁 × PLATEAU × 東京都避難施設の4種融合。Pathways と Flex を命に関わる場面で使う初の例 | データごとに「これがないとこの判断ができない」対比画面 |
| 技術的完成度 | グラフの辺を動的に切る到達圏計算をブラウザ内で秒以下 | 運休入力から地図更新までの応答時間、公開サイトでの実動 |
| UI/UX | 平時と発災時で画面を増やさず、同じ地図が意味を変える | 1分デモ動画、スマホ片手で「待つ場所」が3タップ以内 |

審査員別の刺さりどころ:
- 坂村審査員長・別所審査員: 身体条件を問わない包摂設計、駅構内から屋外への移動の連続性、公開済みの実動。
- 渡邉審査員（国交省）・山口審査員（JR東日本）: 自治体モードが帰宅困難者対策・交通空白対策の EBPM にそのまま使える。帰宅時間帯の駅滞留という現場のリアル。
- チャン審査員（MobilityData）・草薙審査員: RT Alert・Pathways・Flex を一つのグラフで扱う実装と仕様へのフィードバック、MapLibre 上で到達圏が変形する描画と WASM の速さ。

差別化の軸: 運行情報アプリも避難所マップも既にあるが、両者を利用者の身体条件で結び、到達可能性として描く作品はない。

## 10. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 審査時に災害が起きていない | 発災時モードを実データで見せられない | コンテスト期間中の GTFS-RT と運行情報を常時記録し台風・大雪日を再生。模擬運休を注入できるデモモード |
| エレベーター稼働状況のリアルタイムデータがない | 脱出ルートの動的再計算が示せない | 利用者報告と事業者案内の手入力で停止扱いにできる機能を置き、標準化の提言として提示 |
| 3か月でスコープが広すぎる | 未完成の機能が審査で落ちる | 機能1〜3を必須、4〜5を後半に。対象を都営大江戸線沿線に限定 |
| 浸水想定を「現在の浸水」と誤解される | 安全に関わる誤読 | 想定と実況を色と文言で区別。警報が出ている流域のみ有効化 |
| 公開後に実災害で使われ誤案内が起きる | 信頼と安全の損失 | 「公式情報を優先」の文言と出典リンクを常時表示。施設開設状況は「未確認」を明示 |
