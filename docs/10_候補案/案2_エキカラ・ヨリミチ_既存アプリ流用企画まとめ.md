## 1. 一言で

既存の防災位置情報ゲーム「イマノウチ・ヨリミチ」に**公共交通の結節点（駅出口・バス停）を加え、「駅・バス停から避難所／一時滞在施設までの徒歩区間」の段差・幅員・勾配・夜間の安全を市民が歩いて検証し、ほこナビ（歩行空間ネットワークデータ）形式で行政へ還元する**作品に拡張する。
有事モードには ODPT の運行情報を載せ、駅に滞留した人へ「ここから段差なしで行ける滞在先」を示す。コンセプトは流用元の「平時は寄り道、有事はまっすぐ」を「**平時は駅から寄り道、有事は駅からまっすぐ**」に言い換える。

案1「とどく」が到達圏エンジンをゼロから作るのに対し、案2は**動いているアプリ（LINEミニアプリ、公開URLあり）に公共交通層を足す**。完成度と実動で勝ち、技術的新規性では案1に劣る。

## 4. 課題定義（審査基準に合わせた再定義）

解く課題: **「駅やバス停に着いてから避難所・一時滞在施設までの徒歩区間に、段差・幅員・勾配・夜間の安全といった属性データが存在せず、帰宅困難時に駅に滞留した人（特に車椅子・ベビーカー・高齢者）が、どの出口からどこへ行けるかを判断できない」**。

根拠:
- 2026年9月8日の名古屋豪雨では地下鉄が17時15分に全線停止し、帰宅困難者が一時滞在施設で一夜を明かした。8月13日の千葉豪雨では JR 蘇我駅に約4,000人が滞留した。「止まる」は分かっても「どの出口から、どこへ」が分からない（案1 §3）。
- 流用元の取込実測で、避難所・トイレ・AED の370件中232件が属性空欄。駅から避難所までの歩行区間に至っては**データ項目そのものが無い**。
- 都民ヒアリングで、要配慮者がいる家庭の60%が「通れるか不安で遠回りした」経験を持ち、いない家庭では0%。困りごとが当事者に閉じ、行政データに現れない構造（流用元 hearing-citizens.md）。
- 国交省は歩行空間ネットワークデータ（ほこナビ）の整備を推進しているが、駅周辺から避難施設までの区間整備は自治体の予算と人手に依存する。市民の寄り道で埋められれば、整備の社会的意義を示せる。

| ペルソナ | 場面 | 困りごと | 案2での役割 |
| --- | --- | --- | --- |
| A. 駅に滞留した通勤者（主対象） | 帰宅時間帯に運転見合わせ | どの出口から出て、どこで待てばいいか | 有事モードの利用者 |
| B. 車椅子・ベビーカー・高齢の利用者（主対象） | 地下駅の出入口閉鎖、エレベーター停止 | 段差なしで出られる出口と、そこから行ける滞在先 | 有事モードの利用者。平時は検証済み区間の閲覧者 |
| C. 防災士・消防団員・散歩が日課の住民 | 平時の巡回・散歩 | 知っていることを共有する場が無い | 平時のデータ提供者（流用元の初期ターゲットそのまま） |
| D. 自治体防災課・交通事業者 | 帰宅困難者対策、一時滞在施設の配置 | 駅から施設までの経路の実態が分からない | ダッシュボードと CSV の利用者 |

## 5. コンセプトと機能拡張

**コンセプト: 「平時は駅から寄り道、有事は駅からまっすぐ」。**
単位は「経路」ではなく「区間」（駅出口 → 避難施設の1本）。経路探索エンジンは作らず、市民が歩いて検証した区間だけを「検証済み」として表示する。検証されていない区間は表示しない（流用元の原則「データが無いことと設備が無いことは違う」を踏襲）。

| # | 機能 | 流用／追加 | 内容 | 使うデータ |
| --- | --- | --- | --- | --- |
| 1 | 駅出口・バス停のスポット化 | 追加（小） | 都営地下鉄の出入口と都営バス停留所を新カテゴリ `transit` としてピン表示。チェックイン対象にする | ODPT 駅・出入口・停留所、GTFS-Pathways の entrance ノード |
| 2 | 「駅から避難先へ」ミッション | 追加（中） | 駅出口から最寄りの避難所・一時滞在施設まで歩くと区間が1本「踏破」になる。区間の両端でチェックインすると成立 | 既存チェックイン + 既存スポット370件 + 東京都一時滞在施設 |
| 3 | 区間アンケート | 追加（小） | 踏破直後に3値設問: 段差はあったか、車椅子がすれ違える幅か、急な坂はあったか、夜も明るいか、出口にエレベーターはあったか。回答内容で報酬を変えない、合意閾値で検証済み化は既存の仕組みを流用 | 既存アンケート基盤 |
| 4 | 検証済み区間の可視化 | 追加（中） | 地図上で駅出口から避難先へ検証済み区間が線で伸びる。平時は探索済み範囲、有事は全面表示。WOW体験の中核 | 既存 Mapbox 描画 |
| 5 | 有事モード「動いている駅・路線」 | 追加（中） | ライフライン一覧の先頭に「運行中の路線 / 見合わせ中の路線」を ODPT 運行情報から表示。見合わせ中の駅からは「段差なしで行ける検証済み滞在先」を出す | ODPT 鉄道運行情報、GTFS-RT |
| 6 | 出口のバリアフリー情報 | 追加（小） | 駅出口の詳細に Pathways のエレベーター有無・階段段数を表示し、空欄は「未記入」と明示 | GTFS-Pathways（大江戸線）、ほこナビ構内地図 |
| 7 | ほこナビ形式の還元 | 追加（中） | ダッシュボードの CSV 出力に、検証済み区間を歩行空間ネットワークデータのリンク属性（段差、幅員区分、勾配区分、照明）として出す | 既存ダッシュボード + 国交省「歩行空間ネットワークデータ等整備仕様」 |
| 8 | 帰宅困難者ナレッジ | 追加（小） | 「むやみに移動しない」「一時滞在施設とは」「駅の帰宅困難者対応」をナレッジに追加し、駅出口チェックイン時のクイズに出す | 既存ナレッジ基盤、内閣府ガイドライン |

利用シナリオ:
1. 平時: ペルソナCが麻布十番駅の出口でチェックインし、「港区立〇〇小学校（避難所）まで歩く」ミッションを受ける。歩いて着き、両端でチェックイン。段差・幅員・坂・照明の3値アンケートに答える。別の人が同じ答えを出すと区間が「検証済み」になり、地図に線が伸びる。
2. 有事（デモ切替）: 大江戸線が運転見合わせ。有事モードの先頭に「見合わせ中: 大江戸線」「運行中: 都営バス〇〇系統」が出る。現在地の駅出口から、検証済み区間で繋がる一時滞在施設が「段差なし」のラベル付きで並ぶ。
3. 自治体: ダッシュボードで「駅出口から徒歩圏に検証済み区間が1本も無い避難施設」を一覧し、CSV で落とす。

### 6.1 応募条件との照合結果

- **必須条件は満たす。** 応募条件は「公共交通オープンデータセンターまたは GTFS データリポジトリの公共交通データの活用」。都営地下鉄 GTFS / Pathways / 運行情報と都営バス GTFS / GTFS-RT はいずれも ODPT の公開データで、利用規約は CC BY 4.0。
- **推奨データも満たす。** 開催概要で「強く推奨」されるほこナビ・Project LINKS・PLATEAU のうち、ほこナビを構内（大江戸線5駅）と屋外（大門駅周辺、皇居周辺）の両方で使う。PLATEAU は流用元の浸水想定タイルで代替しているため未使用。必要なら港区の PLATEAU 建物モデルを追加できる。
- **流用元のデータはすべて「連携オープンデータ」の範囲。** コンテストページは東京都オープンデータカタログと e-Stat を連携データとして明記しており、避難所・給水・トイレ・AED・町丁目境界はそのまま使える。
- **用途制限に注意。** チャレンジ用に提供された ODPT データ（特に期間限定の Pathways）は「応募作品の開発と当該作品での利用」以外に使えず第三者提供も禁止（規約25・27）。ほこナビの駅構内データも 2027-03-12 までの期間限定。**コンテスト終了後の継続運用では、Pathways と駅構内データが取得できなくなる前提で設計する**（区間データは自前生成なので残る）。
- **設計の修正点。** 「都営地下鉄の駅出入口」は単独のデータセットとして存在せず、Pathways の `stops.txt`（location_type=2）から得られる12駅分のみ。千代田区内に Pathways 対象駅は無い。したがって、**出口単位のスポットは港区の大江戸線5駅に限定し、千代田区側は都営バス停と駅単位（駅情報 JSON の座標）で扱う**。デモと実地検証は麻布十番駅または大門駅に絞る（大門駅は屋外ほこナビデータも存在し、構内と屋外が繋がる唯一の駅）。

## 7. 技術構成（流用度）

| 層 | 現状 | 変更 |
| --- | --- | --- |
| フロント | React + Mapbox GL JS、LINE LIFF | 区間ラインのレイヤー追加、transit カテゴリのピン、有事パネルの運行状況グループ。構造は変えない |
| バックエンド | Hono on enebular、KVS データストア | `segments`（区間）と `segment_survey` の追加。区間は「出口スポットID + 避難施設スポットID」のキーで持ち、既存の surveyStats の事前計算方式を踏襲 |
| 取込 | `tools/ingest`（CSV / GeoJSON） | ODPT API と GTFS zip、Pathways の `pathways.txt` / `stops.txt`（location_type=2 の出入口）を読む取込を追加 |
| リアルタイム | 無し | 有事モードでのみ ODPT 運行情報を定期取得（既存の「歩いている間は通信しない」方針を平時で維持） |
| 出力 | 自治体標準オープンデータセット CSV | 歩行空間ネットワークデータのリンク属性 CSV / GeoJSON を追加 |
| AI | 取込時 Claude、利用時 Gemini 軽量モデル（承認台帳） | 帰宅困難者ナレッジの追加のみ |

経路探索と到達圏計算は作らない。案1の技術的卓越性（Rust/WASM 到達圏）は持たないが、流用元で既に稼働している「市民検証 → 合意 → 行政還元」のループを公共交通に接続することが技術的主張になる。

## 8. 審査基準との対応と審査員

| 審査基準 | 本案の答え | 証拠 |
| --- | --- | --- |
| 社会課題解決 | 駅に滞留した要配慮者が「どの出口からどこへ」を判断できない問題を、2026年の実例と n=37 の実測で語る | 名古屋・千葉の事例、ヒアリングの60% / 0%、属性空欄232件 |
| オープンデータ活用のインパクト | 公共交通 × 避難施設 × 歩行空間 × 浸水想定 × 市民検証の5層。ほこナビ形式で**データを返す**側に回る唯一の作品 | 実際に落とせる CSV、Pathways の出口ノードを起点にした区間 |
| 技術的完成度 | 本番稼働中、スモークテスト付きデプロイ、歩きスマホ防止、AI二段構成、承認台帳 | 公開 URL、デプロイログ |
| UI/UX | LINE で開く、インストール不要、平時と有事で操作系が同じ、検証済み区間が線で伸びる | 1分デモ動画、キャラクターと霧の演出 |

審査員別:
- 坂村審査員長・別所審査員: 駅構内（Pathways）から屋外（ほこナビ）への連続性を、市民が歩いて埋める。空欄を非対応と読まない設計原則。
- 渡邉審査員（国交省）: ほこナビ整備の担い手を市民に広げる提案。帰宅困難者対策と歩行空間整備の2政策に直結。
- チャン審査員（MobilityData）: GTFS-Pathways の entrance ノードを現実世界のチェックイン地点に使い、駅外側へ拡張する実装。Pathways に無い「出口から施設まで」の表現についてのフィードバック。
- 山口審査員（JR東日本）: 駅滞留という現場のリアル、駅員の案内負荷軽減。
- 草薙審査員: Mapbox GL JS 上の区間可視化とキャラクター演出。既に動いていることの説得力。

## 9. 案1との比較

| 観点 | 案1「とどく」 | 案2「エキカラ・ヨリミチ」 |
| --- | --- | --- |
| 中核アイデア | 到達圏エンジン（運休・警報・身体条件で辺を切る） | 市民検証による区間データの生成とほこナビ形式還元 |
| 技術的新規性 | 高い（Rust/WASM、統合グラフ） | 中（既存ループの公共交通接続） |
| 実動の確実性 | 3か月で新規開発。リスクあり | 本番稼働中に追加。高い |
| 先駆データ | Pathways を経路計算に使用、Flex を復旧期に使用 | Pathways を出口ノードに使用。Flex は使わない |
| 社会課題の語り | 2026年の災害事例から「届かない」 | 同じ事例 + 自前のヒアリング実測値 + 属性空欄の実数 |
| EBPM | 想定運休で届かない所を出す分析画面 | 検証済み区間が無い避難施設の一覧、ほこナビ CSV |
| 弱点 | 審査時に災害が無い、エレベーター稼働データが無い | 技術の派手さが弱い、他コンテスト出展作の規約確認、LINE と Mapbox への依存 |
| 審査員への刺さり | 草薙・チャン（技術）に強い | 渡邉・別所・坂村（政策・包摂・実動）に強い |

両案は排他ではない。案2の区間データを案1の到達圏エンジンの辺属性として使う「案3」も成立するが、3か月では案2単体の完成度を優先すべきである。

## 11. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 他コンテストの応募作を流用することが規約に抵触する | 失格 | **確認済み（2026-10-17）: 抵触しない。** 本コンテストの FAQ で「別コンテストに応募した作品を本チャレンジに応募することは可能（別コンテストの規約とデータ利用規約の制約を確認）」と明記。応募規約は「開発者が考案・制作したもの」であることのみ要求（応募条件5）。知的財産権は開発者に帰属（規約21） |
| 都知事杯側の権利・成果の扱い | 公開範囲の制約 | **確認済み（2026-10-17）: 制約なし。** 募集要項の留意事項で「応募作品の知的財産権は応募者に帰属」「都は公式サービスとして公認・公開・頒布しない」。他コンテスト応募や二次利用を制限する条項は無い。都のカタログサイト掲載データと CC 表示データは許諾不要で二次利用可。残る留意点は、都のホームページ等で作品が紹介される可能性と、事業終了後のアンケートのみ |
| 本コンテスト用に提供されたデータの用途制限 | 規約違反 | 本チャレンジ用の提供データは「応募作品の開発と当該作品での利用」以外に使えず第三者提供も禁止（規約25・27）。ODPT 経由で取り込むデータを都知事杯側の成果物や別サービスへ流用しない。流用元のデータ（東京都・区のオープンデータ、e-Stat）は本コンテストの提供データではないため制約なし |
| LINE ミニアプリ依存で審査員が触りにくい | 一次審査の体験 | おためし利用（ログインなし）が既にあるので、審査員向けには PC ブラウザの URL を案内 |
| Mapbox の無償枠超過 | 費用 | 月間マップロードを監視。超える場合は MapLibre へ移行可能な構造（スタイル JSON は共通） |
| 市民検証データが審査までに集まらない | 検証済み区間が少ない | 11月中に防災士・消防団員（流用元の初期ターゲット）と1駅分の実地検証会を1回開く。デモは麻布十番駅周辺に絞る |
| 有事モードがデモ切替のまま | 「検知していない」と誤解される | 流用元の原則どおり「デモ表示」を常時明示。ODPT 運行情報の表示は実データで、切替だけが手動であることを説明 |
| 区間を「安全」と断定して誤案内 | 安全上の誤読 | 「検証済み＝複数人が同じ回答」であって安全保証ではない旨を表示。浸水想定区域内の区間は有事に強調 |
